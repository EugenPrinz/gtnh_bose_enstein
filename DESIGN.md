# BEC Line Controller — DESIGN

Статус: **черновик на согласование**. Кода нет.
Цель: OC-программа, которая автоматизирует **одну линию BEC** (до 16 IO Node) под **все рецепты BEC до конца игры**, заказы — автокрафт с основной ME.

## 0. Целевая версия

| Компонент | Версия (GTNH 2.9.1) |
|---|---|
| GT5-Unofficial | 5.09.54.275 |
| OpenComputers | 1.12.71-GTNH |
| AE2 Unofficial | rv3-beta-1104-GTNH |

Вся механика ниже сверена с исходниками GT5U на теге `5.09.54.275`.
Линия активно меняется: в master за неделю вышли long-fluid (#7384) и фикс Entangler (#8874), в 2.9.1 их нет. Поэтому **все вызовы API идут только через `hal/`**, при обновлении пака правится один слой.

## 1. Механика, на которую опирается дизайн

### 1.1 Сеть и маршруты
- Сеть — связная компонента BEC-труб одного цвета + BEC-шлюзы мультиблоков.
- **Maxwell Gate**: сеть *правого* шлюза видит и забирает конденсат *левой*, обратно — нет. Маршрут через диод существует **только пока диод работает** (`setWorkAllowed`).
- Фильтры диода: по слоту на каждый `CondensateType` — в 2.9.1 их **19** (в master уже 22, программа берёт `getCondensateFilterCount()`). **Пустой список = пропускать всё.** Поэтому один слот навсегда занят фиктивным фильтром (вода), иначе после очистки фильтров рецепта откроется всё.
- Entangler кладёт выход через тот же обход в ширину → ставится слева, вместе с хранилищем.

### 1.2 Containment Field
- Ёмкость = напряжённость поля, **1 L = 1 EU/t**, расход постоянный.
- Переполнение: раз в 20 тиков все типы ×9/10, пока общий объём > ёмкости.
- **Любая остановка (включая обрыв питания) обнуляет содержимое.**

### 1.2a Энтанглер — главное узкое место (`MTEBECGenerator.checkProcessing`)
- Ускоряется **только энергией**: параллели по EU и по объёму исходной жидкости во входных шлюзах, 1 параллель = 1 единица (144 L или 1000 L).
- Распределение EU: типы сортируются по «вход × EU/t», каждому — равная доля остатка; остаток после первого прохода раздаётся вторым проходом тем, у кого ещё есть вход.
- **Цикл = самый долгий рецепт среди типов с параллелями** (40/80/160/240 с), выход — в конце цикла. Короткие типы вместе с долгими идут медленнее.
- Остальные мультиблоки энергией не ускоряются: узел — только наниты; Матрица — сколько узлов одновременно; Поле — ёмкость; затвор — 1A UIV.
- Пример (модель в docs/build.html): Transdimensional Alignment Matrix ×8 при 128A UMV — ~36 мин; Astral Array Fabricator ×16 при 4096A UXV — ~50 мин. Сборка в узлах — секунды.
- → программа держит **запас конденсата** заранее (режим «passive» у Armisael5); WAIT_CONDENSATE — исключение, не норма.

#### Правило подачи жидкостей в энтанглер
Программа считает обе схемы по формуле выше и выбирает быструю:
- **все сразу** — одна партия жидкостей; выгодно, когда длительности одинаковые или вход одного типа мал (его остаток EU уходит другим);
- **по длительности** — группы типов с одинаковым временем рецепта, по очереди; выгодно, когда долгий тип тормозит короткие.
Пример: Sensor Array 2 (40 + 160 с) — 24 мин вместе против 14 мин группами; Shielding 3 (40 + 80 с) — 4 мин вместе против 4 мин 40 с группами.
Для запаса (passive) — то же правило: пополнять типы группами одной длительности.

### 1.3 Observation Array
- Наниты: суммарно ≤ 30 720 (`MAX_NANITES = 2048·15`), действующий тир = **минимальный** среди поданных. Наниты **не расходуются**.
- Каждый IO Node читает **полное** `availableNanites` своего массива: 16 узлов работают одновременно, каждому доступны все N нанитов, делить их не нужно.
- Энергия: узлы питаются по очереди, пока хватает входной EU массива. Узлу без питания — пауза без потери рецепта. Критическая остановка массива → потеря рецептов на всех запитанных узлах.
- У массива **нет OC-методов** → бюджет энергии задаётся в конфиге.

### 1.4 IO Node — прогресс (без изменений между master и 2.9.1)
```
acc      += N
D         = P · 2^|req − prov| · max(contaminants + 1, speedDivisor)
progress += floor(acc / D);  acc %= D
```
- Длительность делится на шаги, у каждого шага свой тир (`getRecipeSteps()` → `{nanite, start, end, index}`).
- Тир ниже требуемого → `nanite-tier-too-low`, прогресс стоит, потерь нет.
- Тир выше требуемого → медленнее в 2^Δ раз.
- **Загрязнители** = видимые массиву типы конденсата, которых нет в рецепте. Если их > 3 → критическая остановка `clogged`, **рецепт потерян**.
- Конденсат забирается каждый тик, сколько есть, ближайшие хранилища первыми. Если его не хватило к концу рецепта → провал, предметы потеряны.
- EU/t = EUt рецепта × P, разгона нет, расход не прекращается во время паузы.
- `maxParallel` по умолчанию 1.

### 1.5 Controller Hatch в 2.9.1 (#8657, бэкпорт)
- Режим `PAUSE` (`PAUSE_INSTANT` / `PAUSE_STEP`) или `PARALLEL`.
- В режиме `PARALLEL` при ненулевом сигнале **перекрывает `setMaxParallel` из OC** (сила редстоуна × 16^схема). → **Не использовать.**
- Один хатч в `PAUSE_INSTANT` подключаем к Redstone I/O как аварийный стоп.

## 2. Эталонная постройка

```
            [левая BEC-сеть, цвет A]                    [правая BEC-сеть, цвет B]
Entangler ──┐                                     ┌── Observation Array ══LoS══ IO Node ×≤16
            ├── Containment Field ── Maxwell Gate ┘        ▲ Nanite Containment Bus
            │   (+ Condensate Detector)                    │
```

### 2.1 AE2 (основа — проверенная схема Armisael5)
| Подсеть | Назначение |
|---|---|
| **Mainnet** | паттерны BEC-рецептов на Dual Interface (Blocking + Smart Blocking), паттерны **умножены** ×K (размер партии) |
| **Pending** | принимает отправленную партию. Рядом стоят несвязанные Dual Interface с **немножёнными** копиями паттернов + адаптеры OC, по ним считается число копий |
| **Shuttle** | 2 IO Port + конвейеры + Machine Controller: по редстоуну диски переезжают Pending ↔ Input. Изолирует одну партию |
| **Input** | Advanced Stocking Input Bus в каждом IO Node через беспроводные коннекторы → 4 хаба Input (решено 2026-11-25); Output Bus (ME) узла — белый коннектор в Mainnet |
| **Entangler** | исходные жидкости из паттерна → Advanced Stocking Hatch Entangler'а (пополнение запаса) |
| **Nanites** | своя подсеть (свой цвет кабеля): ячейка с фильтром на 10 нанитов + Equal Distribution, двусторонний storage bus на Nanite Containment Bus через беспроводной коннектор, P2P Dual Interface + Fake Crafting Card с паттернами «нанит→нанит» (выход переименован в тир), извлечение — storage bus Extract Only + 2 IO Port + Transposer (вариант A, решено 2026-11-25) |

Выход IO Node → mainnet.

### 2.2 Питание (задаётся в конфиге, проверяется планировщиком)
- Observation Array: ≥ Σ (EUt × P) по всем узлам при максимальной партии.
- Maxwell Gate: 1A UIV постоянно.
- Containment Field: = напряжённость поля (EU/t).

### 2.3 OC
- **Стойка + сервер + Component Bus.** Компонентов ~27: 16 узлов + диод + хранилище + ME controller нанитов + transposer + redstone + адаптеры интерфейсов + GPU/экран/клавиатура/fs. Обычный ПК не вытянет.
- Экран T3, интерфейс на русском (как в BHC/DRC).

### 2.4 Порядок постройки
1. Собрать в **креативном мире 2.9.1** и прогнать `becctl probe` / `calibrate`.
2. Только потом строить на сервере.

## 4. Машина состояний линии

```
IDLE ─(redstone: диски в Input)─▶ IDENTIFY ─▶ PLAN ─▶ WAIT_CONDENSATE ─▶ ROUTE ─▶ START ─▶ RUN ─▶ DRAIN ─▶ RETURN ─▶ IDLE
   любое состояние ──(ошибка)──▶ FAULT ──(оператор/авто)──▶ RESUME | HALT
```

| Состояние | Действия | Выход |
|---|---|---|
| IDENTIFY | содержимое Input сопоставляется с немножёнными паттернами → `copies`, список конденсатов | нет совпадения → HALT (смешанная партия) |
| PLAN | раскидать `copies` по узлам; оценить время для constant/swap; проверить Σ EU/t ≤ бюджет | превышение → уменьшить число узлов/P или HALT |
| WAIT_CONDENSATE | ждать, пока в хранилище наберётся нужный конденсат на всю партию (v1) | таймаут → предупреждение, ждём дальше |
| ROUTE | фильтры диода = конденсаты рецепта (+ фиктивный) | проверка чтением |
| START | `setMinParallel = setMaxParallel = P_k`, `setWorkAllowed(true)`; после `hasWork` → `false` | таймаут → HALT |
| RUN | слежение за тиром (constant/swap), `getSlowdowns()`, состояние узлов | `slowdowns > 0` → ALARM: это ошибка маршрута |
| DRAIN | очистить фильтры рецепта, извлечь наниты, убедиться что Input пуст | остатки → HALT, диски не возвращать |
| RETURN | импульс редстоуна → диски уезжают в Pending | — |

**Resume после перезагрузки:** узлы с `hasWork` → фильтры восстанавливаются из `getRequiredCondensate()`, переход сразу в RUN. Фаза и партия пишутся на диск при каждом переходе.

### Инварианты (проверяются перед каждым опасным действием)
1. Фильтры рецепта стоят **до** включения узлов; фиктивный фильтр есть всегда.
2. Видимых загрязнителей 0 (до START проверяется по `getStoredCondensate` + фильтрам).
3. Конденсат на партию уже в хранилище (v1).
4. Σ EU/t узлов ≤ бюджета массива.
5. Containment Field не трогается во время RUN; напряжённость поля меняется только в IDLE и только вверх, либо вниз до значения ≥ текущего объёма.
6. В режиме `PARALLEL` Controller Hatch не используется.

## 5. Выбор стратегии нанитов

Для узла с P параллелями, нанитами N, множителем загрязнения S = 1 (инвариант 2):

```
T_const = Σ_i  len_i · P · 2^(T_max − t_i) / N            (тир T_max всё время)
T_swap  = Σ_i  len_i · P / N  +  n_swaps · t_swap          (тир по шагам)
```
`len_i` — длина шага, `t_swap` — измеренное время замены (AE-крафт + извлечение, обычно секунды), минимум 1 тик на шаг.
- Если `T_const ≤ T_swap` → держим T_max (меньше операций, меньше риска).
- Наниты можно подавать **с опережением**, по `getNextNaniteTier()` / `getNextNaniteSwitchProgress()`.
- Ошибка замены безопасна: при тире ниже нужного узел стоит, а не теряет рецепт.

Параллели: в 2.9.1 пропускная способность ≈ N / (duration · 2^Δ) на узел и не растёт с P. P уменьшает только число замен нанитов, а EU/t растёт линейно. Поэтому партия делится между **всеми** узлами, P на узел минимален.

## 7. Тестирование
1. `sim/` переносит `incrementProgressTime`, маршрутизацию диода, загрязнители и распад хранилища 1:1 из GT5U `5.09.54.275`.
2. Сценарии: обычная партия; загрязнитель → ALARM; > 3 загрязнителей → потеря рецепта (проверка, что ROUTE это предотвращает); обрыв питания массива; перезагрузка OC в RUN; сбой замены нанитов; смешанная партия.
3. В игре: `probe` (все компоненты) → `calibrate` (узлы ↔ массив, сторона диода) → ручной рецепт → одна авто-партия → непрерывный режим.
